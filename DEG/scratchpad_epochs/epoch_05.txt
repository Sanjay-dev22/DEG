2. Key Technical Concepts:
   - Beckn Protocol v2 message lifecycle: `catalog/publish → discover/on_discover → init/on_init → confirm/on_confirm → status/on_status`, ACK-now/answer-later async pattern.
   - onix adapter architecture: `bapTxnCaller`/`bapTxnReceiver`/`bppTxnCaller`/`bppTxnReceiver` "doors"; real Go source (`beckn-onix-src/`, a genuine upstream clone on disk) directly inspected this session:
     - `core/module/handler/stdHandler.go`'s `newHTTPClient()` clones `http.DefaultTransport` unmodified (`Proxy: http.ProxyFromEnvironment` intact, confirmed no active `TransportWrapper` plugin overriding it) — proves onix's HTTP client genuinely respects `NO_PROXY`.
     - `pkg/plugin/implementation/router/router.go`'s `handleProtocolMapping()` — when a message already carries `bapUri`/`bppUri`, the route is built directly from that string; **no DeDi registry lookup happens for buyer↔seller message delivery**, only for signing-key lookups elsewhere (`dediregistry.go`'s `Lookup`/`LookupNode`/`QueryByNetwork`).
   - Docker Desktop auto-injects `HTTP_PROXY`/`HTTPS_PROXY` into every container based on host/system proxy config, pointing at a local relay (`host.docker.internal:3128` in this case, run by `px`, a real open-source NTLM-authentication proxy helper) — invisible from `docker-compose.yml` alone, confirmed via `docker inspect <container> --format "{{.Config.Env}}"`.
   - `NO_PROXY`/`no_proxy` environment variables as the standard proxy-bypass mechanism — added to all six `onix-*` services AND `beckn-router` (Caddy) in `docker-compose.yml`, since Caddy makes its own separate second outbound hop per request (e.g. `beckn-router:9000` → `onix-sellerapp:8082`) and is also subject to the same Docker-Desktop-injected proxy.
   - Mixed-content browser security: a page served over `https://` can never open a plain `ws://` WebSocket — must use `wss://`; fixed by deriving protocol from `location.protocol`.
   - Cloudflare Quick Tunnel (`cloudflared tunnel --url http://localhost:<port>`) — zero-signup, free, gives an ephemeral public HTTPS URL (`*.trycloudflare.com`) forwarding to a local port; confirmed already installed at `/c/cloudflared` on the dev machine. Contrasted with `ngrok` (not installed, would need account/authtoken).
   - Real, structural reason `discover` never worked: the buyer's own `bapUri` context field (`http://buyerapp.example.com:9000/bap/receiver`) only resolves inside the local Docker network via Caddy aliases — a real external discovery service has no way to reach it. Fixed by tunneling `onix-buyerapp:8081` itself and setting `bapUri` to that public tunnel URL + `/bap/receiver`, via a new `PUBLIC_BAP_URI` env var.
   - Real callback action name discovered via live log: `on_discover` (not `catalog`, which was an earlier untested guess) — required adding it to the buyer's routing config's endpoints list.
   - Extended schema validation (`extendedSchema_enabled` in onix's `schemaValidator` plugin config) validates an entire inbound payload atomically — since `on_discover` returns one large, shared, multi-tenant aggregated catalog from many real testers, a single non-conformant historical entry anywhere in it (e.g. missing `participantId`) blocks the whole thing, including the buyer's own valid fresh offers. Disabled specifically on the `bapTxnReceiver` module (base schema validation stays on).
   - Real, verified evidence of a genuinely shared, multi-tenant test network: discovered offers include ones from a clearly different real participant (`bpp.ies.gigawatt.network` / `bap.ies.gigawatt.network`), plus historical entries with names embedding other testers' identifiers (`ameet-3sept`, `test17jul`, `22jul-ameet`).
   - `node:sqlite` (Node's built-in SQLite module, Node ≥22.5) — used instead of `better-sqlite3` specifically to avoid native-addon compilation needing `github.com`/`nodejs.org` (blocked on corporate networks).
   - Real settlement math formula: `FINAL_ALLOC × PRICE_PER_KWH`, computed both by the real onix `contractpolicyenforcer` plugin (fetching a live `.rego` policy from `api.dedi.global`) and redundantly in our own app code for immediate UI display (since there's no callback path back to the seller after `on_status`).
